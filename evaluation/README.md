# Evaluation labels and review

The development set has 10 questions. The locked set has 34 questions. The first 30 cover Campaign 1 in the guide's five groups, in order: 8 single-scene facts, 6 relationships or knowledge questions, 6 multi-part questions, 5 incorrect recaps and 5 unresolved questions. T01 and T02 ask the same question in English and Hinglish. T08 and T28 revisit the gold count on opposite sides of the reveal. T31 through T34 test the town, inn and ship in Campaign 2, including a question before the ship is named. Language is the requested output language. Original evidence stays in English.

A span such as `10:279-281` means episode 10 of the campaign in that row, original turns 279 through 281 inclusive. A vertical bar separates required parts. A semicolon separates alternative source spans for one part. A blank range denotes an unresolved question. A later recap keeps its own episode. The app receives only the writer's question, settings and eligible passages.

Hit@5 requires at least one returned turn range to enclose an annotated span. Complete coverage requires every part's span on a multi-part question. These are location metrics. A short subspan inside a very long turn can share the same turn ID while omitting the relevant sentence. A valid equivalent exchange can also fall outside the annotated ranges. Citation and answer review use the actual supplied passage text for this reason.

An answer is accurate when it answers all requested parts correctly, supports each factual part with a supplied source, and uses the requested verdict. A correct abstention explains what is missing. The review also records how many factual output claims have support, independent of whether the answer addresses every part. Generic citation-validation fallback messages alone do not establish a correct abstention. Monitor language separately when reading multilingual cases. Text leaks are affirmative assertions of a later fact; the future-word flag only helps locate candidates. Warm timing includes model generation and validation retries. The independent search warmup precedes timed cases in each process; later versions can reuse warmed models. These warmups are separate from a fresh web server launch.
